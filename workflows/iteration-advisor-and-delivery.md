# 迭代建议与 Goal 交付循环

> 状态：采访中，尚不可实施。所有未决问题解决后才视为完成。

## 目标

每天基于当前仓库证据找出下一项最值得验证的小增量；由用户做一次决策后，可把被选方案转换为一个明确 Goal，并持续完成实现、自测和验收汇报。

这套循环优化的是“下一步决策质量与交付闭环”，不是想法数量。它应抑制无证据的功能堆积。

## 已确认事实

- Norma OS 当前保持高频、跨能力迭代，且已有 SPEC、设计说明、执行计划和自动化测试体系。
- 仓库规定新功能和 bugfix 使用 TDD；用户可观察流程需要 e2e 证据。
- Goal 只有在用户明确授权具体目标时才能创建；建议本身不会启动 Goal。
- 执行期间必须保护工作区中原有的未提交改动。

## 建议中的运行流程

### 1. 定时触发候选分析

- 频率：每天，包括周末。
- 时间：20:00。
- 时区：`Asia/Shanghai`（根据当前工作区时区确定）。
- 每次触发只生成建议，不自动创建 Goal，也不修改产品代码。

用户也可以随时说“盘点下一步”手动追加一次分析；手动运行不改变次日的定时计划。

### 2. 自动收集证据

在不打扰用户的情况下读取：

- 最近完成的目标、提交和 diff；
- 相关 SPEC、设计文档、执行计划与验收报告；
- 当前测试结果、未覆盖路径、TODO/FIXME 与机械化护栏；
- 架构边界、当前未提交改动和已知阻塞；
- 能反映真实使用价值的用户反馈或产品信号（来源待确认）。

### 3. 形成候选并排序

日更不承担“每天必须提出新功能”的配额。若证据不足，必须明确建议以下最有价值的一项：修复缺陷、补充测试、偿还技术债、收集反馈，或当天不采取行动；不得用猜测填满 3 个候选。

输出最多 3 个候选，每个候选必须包含：

- 它解决的用户问题，而不只是功能名称；
- 证据与当前为什么值得做；
- 最小可验证增量与明确不做范围；
- 预期价值、风险、依赖和可逆性；
- 可自动化的验收标准与必要的人工验收；
- 推荐顺序，以及“不继续加功能”的选项是否更好。

默认推荐一个候选，但不替用户做产品方向决策。

### 4. 单一决策检查点

向用户提供决策简报，而不是长篇草稿。用户可以选择、修改或拒绝候选。

只有用户明确选择具体候选并授权“启动 Goal”后，才创建 Goal。模糊认可（例如“看起来不错”）不构成执行授权。

### 5. Goal 内端到端交付

创建 Goal 后：

1. 把选定增量收敛为具体目标、范围和验收标准。
2. 检索仓库事实和适用规范；若存在会实质改变结果的产品决策，回到用户检查点。
3. 按仓库要求先写能失败的聚焦测试，再实现。
4. 对用户可观察流程补充或更新 `crates/e2e` 证据。
5. 运行与变更风险相称的 crate 测试、静态检查、性能护栏和必要的构建验证。
6. 修复由本次变更引入的失败；不覆盖或回退用户原有改动。
7. 验收标准全部有证据且无必需工作遗留后，才把 Goal 标记为完成。

### 6. 完成简报与再循环

完成时只呈现决策级信息：交付了什么、关键证据、仍有何风险、如何体验，以及下一个循环是否值得启动。新建议回到第 1 步，不自动创建下一个 Goal。

## 自动化边界

- 可以自动完成：本地代码与文档修改、TDD、单元/集成/e2e、仓库护栏、可在本机运行的构建和结果归因。
- 可能需要检查点：产品取舍、破坏性操作、外部账户或凭据、付费/发布动作、无法由自动化可靠判断的视觉体验。
- 不能虚报：headless GPUI e2e 不等同真实 `.app` 启动；没有运行 L3 runner 时必须明确区分。

## 未决问题

1. 候选排序的首要产品信号及其来源。
2. 进入 Goal 前是否需要完整 SPEC，还是允许小修复使用轻量验收清单。
3. Goal 的默认执行边界是否包含文档更新、提交代码与打包验证。
4. 哪些失败或风险必须中止并向用户请求决策。
5. 完成简报希望出现在哪里，以及是否需要保留历史决策日志。
