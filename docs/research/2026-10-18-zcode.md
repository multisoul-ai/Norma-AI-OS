## 0. 测试方法与环境（重要前提）

- 官方仓库 `https://github.com/zai-org/ZCode`，Apache-2.0，`main` 提交 `aac4755666d0`（`feat: update to v3.15.1`），CLI 源码在 `apps/zcode-cli/`。
- **没有账号凭据**。所有「模型回合」用本地 mock 模型验证：`evidence/.../mock.py` 是一个监听 `127.0.0.1:18765` 的 OpenAI Chat Completions SSE 服务，按提示词关键字返回文本或 `Bash`/`Read` 工具调用。ZCode 通过 `~/.zcode/cli/config.json` 的 `provider.mock` 指向它（`apiKey` 为占位字符串，非真实凭据）。这验证的是 **ZCode 自身的 hook、会话、审批、退出行为**，不代表真实 GLM 模型的行为。
- 测试时 `HOME=/tmp/zc-home`，工作目录 `/tmp/zc-work`（均为全新空目录）；真实 `~/.zcode` 未被创建（`ls ~/.zcode` 报不存在，已验证）。
- 终端交互用 `tmux -L zc` 驱动（`send-keys` / `capture-pane`），启动方式与 Norma 一致：`/bin/zsh -lic 'exec zcode'`。

## 4. 会话续接

全部已验证（mock 模型，`/tmp/zc-work`）：

| 场景 | 命令 | 结果 |
| --- | --- | --- |
| 续接当前目录最近会话 | `zcode -c`（TUI） | SessionStart 载荷 `source:"resume"`，`sessionId` 为此目录最近一次更新的会话（`sess_33c0d69e…`）。mock 请求日志 `nmsgs` 从 17 增长到 19，历史确实载入模型上下文。**UI 不回放历史**，仍显示空白启动界面 |
| 按 ID 续接 | `zcode --resume sess_4f863ed2-…`（TUI） | SessionStart `source:"resume"`、`sessionId` 与参数一致，mock 请求 `nmsgs=7`（该会话原有消息加新提示） |
| 无可续接会话 | `zcode -c -p hi`（空目录） | `Error: No resumable session found for /private/tmp/zc-empty`，exit 1 |
| 无可续接会话（TUI） | `zcode -c`（空目录） | **TUI 照常打开，第一次提交提示词才报** `Error: No resumable session found …`（延迟报错） |
| 不存在的 ID | `zcode --resume sess_0000…` | headless：`Error: Session not found: …`，exit 1；TUI 同样延迟到首次提示词才报 `Session not found` |
| 权限模式是否随会话恢复 | `--resume` 一个用 `-p`（默认 yolo）创建的会话 | **恢复后 SessionStart `mode:"yolo"`**：权限模式随会话持久化，与新建的 `build` 不同 |

- 会话 ID 来源：hook 载荷 `session_id`/`sessionId`，格式 `sess_<uuid>`；hook 子进程环境变量也有 `ZCODE_SESSION_ID`、`CLAUDE_SESSION_ID`。**SessionStart 在首次提交提示词时才触发**，不是 TUI 启动时（已验证：启动后 8 秒内无事件，提交提示词后才出现 SessionStart `source:"startup"`）。
- 源码佐证：`packages/cli/src/resume.ts` 的 `-c` 通过 `resolveLatestSession({directory})` 查 SQLite `listSessions(limit 1, roots true)`，即**按目录取最近**；多张 ZCode 卡片同目录时 `-c` 会串会话，**Norma 不得使用 `-c`，只用 `--resume <id>`**。
- 未验证：TUI 内 `/new`、`/resume`、`/fork` 之后 hook 载荷里的 `session_id`/`source` 如何变化（本次只验证命令行参数路径）。

## 5. 会话存储位置与格式

已验证（`find /tmp/zc-home/.zcode`）：

- `~/.zcode/cli/db/db.sqlite`（+`-wal`、`-shm`）：会话库，源码 `bootstrap/src/sessions.ts` 通过 `SqliteSessionStore` 读写。
- `~/.zcode/cli/rollout/model-io-sess_<uuid>.jsonl`：按会话 ID 命名的模型 I/O 记录。
- `~/.zcode/cli/exec/sess_<uuid>/`、`~/.zcode/cli/log/zcode-<日期>.jsonl`。
- 配置：`~/.zcode/cli/config.json`（源码默认 `DEFAULT_BASE_DIR = "~/.zcode/cli"`，`adapters/src/config/file-config.adapter.ts`）。

结论：**不扫描目录、不查库即可得到当前会话 ID——能**，且只有一条路径：hook 载荷（或 hook 子进程环境 `ZCODE_SESSION_ID`）。会话库是 SQLite，Norma 的「禁止查 SQLite」约束下不能用它做发现。因此降级策略见 §10：无 hook 缓存的卡片恢复退化为普通启动。

## 6. Hooks 机制（核心）

### 6.1 事件与配置位置（已验证 + 源码佐证）

- 事件名恰好 7 个：`SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PermissionRequest`、`PostToolUse`、`PostToolUseFailure`、`Stop`（`packages/contracts/src/hooks/index.ts` 的 `HookEventName`；另一份官方插件文档 `diagnosing-hooks` SKILL.md 明确写「exactly seven」，且 `Notification`、`SubagentStop`、`PreCompact` 不支持）。
- 配置位置：用户级 `~/.zcode/cli/config.json` 顶层 `hooks` 键，形如 `{enabled, timeoutMs, maxOutputBytes, events:{<Event>:[{matcher?, hooks:[…]}]}}`；工作区级 `<repo>/.zcode/config.json`；插件 `hooks/hooks.json`。
- **`hooks.enabled` 默认关闭**：已验证——把 `hooks.enabled` 删除后启动 TUI 并提交提示词，hook 目录**零事件**；设为 `true` 后全部触发。
- hook 类型：`command`（shell 字符串，`timeout` 单位秒）与 `process`（`command`+`args[]`，`timeoutMs` 毫秒）。
- 已验证：`matcher:"*"` 能匹配 `PreToolUse`（事件照常触发）；省略 `matcher` 匹配全部。
- 已验证：hook 命令是不存在的路径（`/nonexistent/multisoul-agent-hook forward --source zcode`）时，**回合不受影响**，工具照常执行，`Stop` 照常触发。卸载/二进制丢失不会卡住 ZCode。
- 已验证：写入配置中 `userKeep` 这类未知用户字段，运行一个会话后仍保留（ZCode 不在会话期间重写 config.json）。
- 已验证：启动 ZCode 时父环境的 `MULTISOUL_HOOK_TOKEN`、`MULTISOUL_HOOK_ENDPOINT`、`MULTISOUL_NODE_ID`、`NORMA_SOCKET` 等变量会原样传入 hook 子进程，因此 `multisoul-agent-hook forward` 的现有环境传递机制可直接工作。
- hook 额外环境：`ZCODE_SESSION_ID`、`ZCODE_PROJECT_DIR`、`CLAUDE_SESSION_ID`、`CLAUDE_PROJECT_DIR`（已验证）。

### 6.2 真实载荷（节选，完整样例见 `hook-payloads/`）

stdin 同时包含 ZCode 的 camelCase 字段与 Claude 风格 snake_case 别名（`hook_event_name`、`session_id`、`tool_name`、`tool_input`、`permission_mode`、`transcript_path`、`tool_use_id`）。**`event.rs::parse_hook_event` 已能直接解析**（读 `hook_event_name`/`session_id`/`tool_name`/`error`）。

```json
// SessionStart（首次提示词时，source: startup|resume|clear|compact）
{"cwd":"/private/tmp/zc-work","hookEventName":"SessionStart","mode":"build","model":"mock/mock-model","sessionId":"sess_33c0d69e-…","source":"startup","traceId":"…","turnId":"turn_…","hook_event_name":"SessionStart","permission_mode":"build","session_id":"sess_33c0d69e-…"}
// UserPromptSubmit: 另含 "prompt":"RUNTOOL please"
// PreToolUse: "toolName":"Bash","toolInput":{"command":"echo hi-from-tool","description":"echo"},"toolCallId":"call_1","riskLevel":"high","sideEffectScope":"system"
// PermissionRequest: "reason":"High risk tools require explicit approval","requestId":"perm_…","toolName":"Bash",…
// PostToolUse: "toolResponse":{"stdout":"hi-from-tool\n","exitCode":0,"status":"completed",…}
// PostToolUseFailure: "error":"File does not exist. …","error_details":{"message":"…","type":"tool_execution_failed"},"isInterrupt":false
// Stop: "responseText":"tool finished OK","toolCallCount":1,"stopHookActive":false,"last_assistant_message":"tool finished OK"
```

是否含 sessionId、cwd、工具名：全部已验证含（sessionId/cwd 每个事件都有；工具名仅工具类事件有）。注意 `cwd` 在 SessionStart 等事件里是 `/private/tmp/zc-work`（真实路径），工具类事件里是 `/tmp/zc-work`（符号链接路径），**Norma 不能用 cwd 字符串精确比较关联节点**，应继续用 `MULTISOUL_NODE_ID`。

### 6.3 安装与卸载而不覆盖用户配置

方案：在 `~/.zcode/cli/config.json` 做 JSON 合并（沿用 `atomic_file` + `add_command_hook`）：

- 仅向 `hooks.events.<Event>` 数组**追加**一个 Norma 分组 `{"hooks":[{"type":"command","command":"'<path>/multisoul-agent-hook' forward --source zcode","timeout":5}]}`；用 `command` 字符串精确匹配做幂等判断与卸载（已有 `command_exists` 逻辑）；不触碰用户其它事件项、`provider`、`model`、未知字段。
- 需设置 `hooks.enabled=true`（否则无效，已验证）。**副作用**：若用户原本写了 hooks 但保持 `enabled:false/缺省`，安装会让这些用户 hook 开始执行。降级处理：安装时若 `hooks.enabled` 非 true，在 UI 设置页文案中说明；卸载时只删除 Norma 条目，**不回写 `enabled`**（无法判断是谁设置的）。
- 不使用工作区级 `<repo>/.zcode/config.json`（会污染用户项目）。
- 备选：插件 hooks.json（任意插件含 hook 时自动启用运行器，无需改 `enabled`），但需要安装插件目录与 marketplace 机制，复杂度高，未验证安装流程，**不采用**。
- 未验证：ZCode 桌面应用或 TUI 内「设置」界面写回 config.json 时是否保留未知的 Norma hook 项（本次只验证命令行会话期间不重写）。

## 7. 权限模式与审批

- 默认权限模式：TUI 为 `build`（输入框标题 `Build`；SessionStart `mode:"build"`）。`-p` 的默认为 `yolo`（`--help` 明文）。已验证。
- 跳过审批：`--mode yolo`（`--help`：`Permission mode … build, edit, plan, yolo, or guarded`）。**只记录，Norma 默认启动命令不带任何 `--mode`**。未实测 yolo 在 TUI 的行为。
- 低风险命令（`echo`）在 build 模式下**无需审批**但仍触发 PreToolUse；`touch` 文件弹出审批框：标题 `Approval required: Bash`，选项 `Allow once` / `Always allow in this project` / `Deny`，`Esc` 为拒绝（已验证）。
- 如何判断等待审批：**`PermissionRequest` hook**，载荷含 `toolName`、`reason`、`requestId`（已验证，触发时机在审批框出现时）。无「审批结束」专用事件：允许后出现 `PostToolUse`；**拒绝后没有 `PostToolUseFailure`，直接 `Stop`**（已验证，文件未创建，随后只有 `Stop`）。

## 8. 事件到 Norma 状态映射

现有 `task_state_for_provider_event` 的映射对 ZCode 载荷**无需改动**即可成立：

| ZCode 事件 | Norma 状态 | 状态 |
| --- | --- | --- |
| `SessionStart` | Ready | 已验证（但仅在首次提示词时到达） |
| `UserPromptSubmit` | Thinking | 已验证 |
| `PreToolUse` | RunningTool（tool_name） | 已验证 |
| `PermissionRequest` | WaitingApproval | 已验证 |
| `PostToolUse` / `PostToolUseFailure` | Thinking | 已验证 |
| `Stop` | Done | 已验证 |
| Failed | **无事件**。mock 模型返回 HTTP 500 后 ZCode 重试 ≥25 次、约 3 分钟内既无 `Stop` 也无失败事件，TUI 一直 `esc to interrupt` | 已验证：不支持 |
| Ended（SessionEnd） | **无事件**；`Ctrl+C` 退出不触发任何 hook | 已验证：不支持 |
| 用户 `Esc` 中断 | **无 `Stop`**（SLOW 回合按 Esc，TUI 回到空闲，hook 目录只有 `UserPromptSubmit`） | 已验证：不支持 |

降级：Failed / Ended / 中断无 hook 信号，卡片会停留在 Thinking；由 Norma 现有的「PTY 进程退出」与「用户输入」路径纠正，不新增终端屏幕解析（TUI 忙碌标识 `esc to interrupt` 可见，但按规则不作为状态来源）。

## 12. 本 CLI 接入方案

### 启动命令

`/bin/zsh -lic "exec zcode"`，保持不变，**不带 `--mode`**（默认 build，需审批）。骨架已是此形态（`crates/runtime/src/nodes/agent.rs:49`）。

### 恢复命令

`/bin/zsh -lic "exec zcode --resume <sess_uuid>"`：

- `<sess_uuid>` 仅来自 hook 缓存的 `session_id`（已有 `agent_hooks`/session_snapshot 路径）；必须校验匹配 `^sess_[0-9a-fA-F-]{36}$` 后再拼进命令，避免 shell 注入。
- 不使用 `-c`（按目录取最近，多卡片会串）。
- 无缓存 ID 时退化为普通启动（不加参数）。
- 风险：ID 失效时 TUI 照常打开，首次提示词才报 `Session not found`（延迟报错，已验证），Norma 无法提前探测。ID 只来自本次运行实际收到的 SessionStart，失效概率低；仍在用户文档里说明。
- 注意：恢复会沿用原会话权限模式（§4）；Norma 创建的会话均为 build，恢复仍是 build。

### 会话发现

`crates/runtime/src/session_snapshot.rs`：ZCode 分支保持「不扫描目录」，仅使用 hook 缓存；`discover_session_id` 返回 `None`（骨架已如此）。不读 `db.sqlite`、`rollout/`。

### 编排（OrchestrationProvider）
