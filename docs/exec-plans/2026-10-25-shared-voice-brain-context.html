目标结构与拼接契约

七组内容如何进入模型

分组 默认策略 更新与裁剪规则
① 系统规则 + 个性 固定稳定前缀 保留公共规则与模式规则；配置变化后重建相应版本
② 环境 + 卡片索引 固定小快照 保留当前范围和必要路由信息；其他卡片按需展开
③ 当前目标 + 有效约束 固定小快照 带任务、来源、版本和撤销关系；附当前话题与最近相关播报引用
④ 相关记忆 本轮相关时才加入 精确引用优先，现有关键词检索其次；摘要带来源，原文按需读
⑤ 幕僚决定与播报 本轮相关时才加入 从话题、播报或任务引用查依据和真实回执；缺关联就明确缺失
⑥ 近期历史 保留各自原生形式 Legacy / 豆包按完整轮次；Live 保留音频会话；后台使用时间线快照
⑦ 当前输入 保留各自原生形式 Legacy / 豆包传 user 文本；Live 继续传音频，转写不重复提交

“固定”指每轮需要的逻辑内容，不表示 Chat 只发送一次。②—⑤是带来源的数据，不获得①的指令地位。播报记录不能伪装成用户发言。

每次模型请求固定一个 snapshot。豆包工具后续请求仍刷新环境，并生成关联同一 turn 的新 snapshot。执行前再核验最新约束、任务和审批，不能仅靠请求开始时的版本。

最小数据契约

类型 内容与不变量
ContextScope workspace_id、area_id、project、worktree、task_id、conversation_id；无项目显式为 personal；稳定 ID 优先于目录名
ContextEvent 宿主生成 event_id；原始来源、序号、时间、scope、类型化内容、相关事件引用；重复 ID 幂等

ContextManifest 来源 ID、版本、入选理由、字节或 token 单位、裁剪与超时标记、耗时；默认不含私人正文

consumer 区分 Legacy、豆包、Live 通话、Live 后台规划与幕僚。模式切换仅携带允许共享的事实与必要摘要，不迁移旧工具调用、授权身份或播放任务。

装配 Interface 接收输入、scope、consumer、预算及已读取材料，返回 ContextBundle 与 ContextManifest。纯装配不查数据库、不联网、不控制音频。宿主负责有界读取和最新状态核验。

E

关键流程与失败处理

1. 用户输入 → 有效工作状态

先记录最终用户输入及来源，再准备本轮上下文。现有模型回合通过拟新增的类型化工作状态工具提交候选，不额外增加一次分类模型请求。直接路由先读取当前有效限制；存在未解析修订时，暂停该次直接执行并回到现有解析流程。

宿主验证来源事件、目标 scope、expected_revision 和允许的变更类型。同一条约束的修订保留 supersedes 关系；模型摘要不自动撤销用户规则。ASR 临时结果不写成长期事实，转写更正保留来源关系。

工作状态区分两类：文本要求用于对话和任务交接；可执行限制绑定宿主已识别的操作与目标。宿主能校验的限制才标记为 enforced；其余标记为 communicated，不能声称已强制执行。

例如“这次先别发布”保留原话并进入后续任务上下文。若无法可靠映射到具体动作，不自动放行相关操作。已经派给外部 Coding Agent 的任意内部命令，仍受现有执行与审批机制约束；本方案不宣称能拦截所有外部 shell 行为。

限制性规则可在核验来源后收紧；放宽权限仍走现有用户授权与审批入口。用户说“刚才那个”有多个候选时，先澄清任务，不能以最后生成时间直接决定。

内存接受和持久化成功分开记录。事务提交成功才可说“已保存”；失败保留待保存状态并有限重试。重启后若关键状态不完整，相关执行等待核验，不把缺记录解释为无限制。

2. 幕僚决定 → 播报 → 追问

宿主为决定、回执和汇报生成稳定引用。Report 可以引用多个决定，引用必须属于可读作用域。旧 Report 没有来源时保留正文，标记关联缺失，不根据相近文本补造关系。

播报事实先进入共享记录，再由当前模式交付。Legacy 走原 TTS；豆包走常驻播报通道；Live 走原生追加与输出通道。语音关闭时记录 skipped；Live 未连接时记录未播，不自动开通话或麦克风。

交付状态分为 created、queued、playing、completed，以及 skipped、interrupted、failed。Live 另记录 sent / acknowledged；协议接收不等于开始或完成播放。没有可靠的报告与音频对齐时，播放归属标 unknown，不伪造进度。

用户追问优先结合当前话题、任务和实际播报状态，再沿 report → decision → receipt 取依据。生成过但没播出的汇报不能被默认当作“刚才说过”。记录读取不会触发重新执行。

3. Live 更新 → 当前回答

T00 实测协议是否支持在回复开始前完成更新、取消旧回复或读取响应关联。若可保证顺序，绑定上下文 revision 与当前 generation 后发送。不能证明顺序时，相关事实问答必须完成后台只读核验。

如果供应商无法可靠完成上述核验与回答交接，该能力保持关闭，T07 不算通过。不能用本地静音、收到 ACK 或“请使用最新信息”的提示词代替时序保证。

按 scope + revision 去重。当前本地 Append 单条上限为 500 UTF-8 字节；分段须计算完整内容，包括版本标签。追加失败、部分批次成功或超时应记入 manifest；不把部分材料标记为完整快照。

只追加协议下的旧值作显式失效说明，宿主仍依据最新状态执行。累计材料达到阈值时按已验证的恢复能力重建；先保存有效事实，不重放旧操作或旧播报。

4. 预算、读取与降级

情况 行为
普通闲聊没有相关材料 省略④⑤；只带必要状态和原生历史

Live 原生幕僚报告与局部取消

  • 已连接 Live 时，报告进入原生通道，不依赖旧 TTS 就绪状态。不自动开启通话；完整 scope 不匹配、输出阻断或未连接时不接收。
  • GPUI 前台仅投递原文及句柄，分段在后台完成。每段含报告 ID、版本、序号和总数；完整 JSON 内容最多 500 UTF-8 字节，最多 64 段。
  • 逐段核对 ACK 的 ID 与类型。正文全部 ACK 后才发送 Commentary 提示；最终 ACK 记 Sent → Acknowledged → Unknown。普通音频不能证明该报告已开始或完成播放。
  • 未提交网络队列的报告被取消时记 Skipped，部分提交后取消记 Unknown。报告入队起 15 秒到期；慢 ACK 或长报告可能到期，当前尚未优化。
  • 网络队列中的报告带独立取消令牌。出队和等待 socket ready 均检查取消；帧已交给 socket 后完成 flush，不能撤回已经发送的字节。
  • 报告最多使用 12 个网络队列槽，保留 4 个给静音和停止输出控制。单份报告仅允许一段在途，容量不足只重试未被接收的命令。
