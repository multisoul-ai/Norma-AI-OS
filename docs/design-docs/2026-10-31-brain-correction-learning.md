建议先完整保存提议与纠正，可靠关联同一事项。再形成有来源的候选偏好，有限影响后续建议。用户始终能查看、纠正和删除。学习不会替代派发确认。

## A 首阶段做什么，现有代码缺什么

**先看全貌：用户的纠正怎样改变下一次建议。**

```flow
(幕僚原建议) -> 用户明确替代: 绑定同一事项
用户明确替代 -> [(完整纠正记录)]: 先保存事实
完整纠正记录 -> 归纳处理差异: 后台执行
归纳处理差异 -> *候选偏好: 保留来源和不确定性
候选偏好 -> 下一次同情境建议: 达到使用条件
下一次同情境建议 -> {用户确认派发?}
{用户确认派发?} -> 执行任务: 是
{用户确认派发?} --> 用户明确替代: 再次纠正
```

图中的“候选偏好”只影响怎么建议。用户确认仍在执行前，归纳过程不会派活。

```callout info 推荐首阶段：明确关联的项目内学习
覆盖“忽略提议 → 在原提议上补充替代方案 → 归纳差异 → 后续建议变化”。
首阶段包含持久化、去重、重启恢复、冲突处理和删除失效。跨项目个人偏好、自由文本自动配对和自动 Dream 留到后续。
本页是待评审方案。本轮只产出文档，未修改业务代码，也未执行这里列出的功能测试。
```

“最小”指缩小入口和适用范围，不省略来源、删除或执行权限边界。先支持桌面提议详情、被忽略提议的历史详情，以及带该提议引用的 Dock 输入。用户仍可直接输入其他任务，无须解释每次忽略。

## B 一次纠正需要保存哪些数据

以下类型、字段和表名均为**拟新增设计**。不把未知值补成推测，也不把模型摘要当作原始证据。

**数据关系图：先保存经历，再从经历提炼偏好。**

```er LR
原提议
  proposal_id PK
  完整任务与理由 text
  任务与对话身份 ref
*纠正经历
  episode_id PK
  proposal_id FK -> 原提议
  替代方案与明确原因 text
  后续结果与来源 refs
证据关系
  episode_id FK -> 纠正经历
  candidate_id FK -> 候选偏好
  支持或反例 enum
候选偏好
  candidate_id PK
  情境与适用范围 rules
  版本与状态 state
使用记录
  use_id PK
  candidate_id FK -> 候选偏好
  下一次提议与使用版本 refs
```

一条偏好可以有支持和反例；它们都指向完整纠正经历。同一根任务的重复记录不会变成新的独立证据。

**ProposalRecord：原提议的不可变快照**

| 字段 | 含义与来源 |
| --- | --- |
| proposal_id、revision | 宿主生成稳定 UUID；版本标识本次完整提议，替换提议不复用身份 |
| scope | 完整 ContextScope：workspace、area、project/worktree，以及可得的 task、conversation |
| subject | 宿主绑定的原事项身份；保存根任务 ID、父任务 ID、run/session/turn ID 的已知部分 |
| identity_quality | complete / partial / unavailable；未知任务或会话 ID 为 null |
| target | Agent 稳定身份、profile、可选 card/run ID；显示名称另存，不能作为关联主键 |
| title、task、why | 用户当时看到的标题、完整任务和幕僚理由，逐字保存 |
| sources | 形成提议时的用户请求、上下文与任务结果引用；无来源必须标缺失 |
| created_at、origin_turn | 时间用于展示、排序；origin_turn 对应幕僚会话轮次 |
| lifecycle | pending / dispatched / dismissed / superseded；同 Agent 新提议挤掉旧提议属于 superseded，不是用户拒绝 |

**CorrectionEpisode：一次事项中的纠正经历**

| 字段组 | 必须保存的内容 |
| --- | --- |
| 身份 | episode_id、schema_version、revision、scope、proposal_id + revision、独立事项键 |
| 用户反馈 | action_id、来源入口、原始文本、dismissed / deferred / rejected / replaced / unrelated / unresolved |
| 关联判断 | verified / uncertain / unlinked；关联方式、核验引用、候选提议、未能判断的原因 |
| 用户替代方案 | replacement 的完整文本、原始输入引用、提交状态；未执行的替代方案仍可成为用户选择证据 |
| 明确原因 | explicit_reasons 数组：用户原话、原文位置、来源引用；没说原因就为空 |
| 归纳差异 | 原方案与新方案在范围、顺序、验证、优先级上的差异；标记为模型推断 |
| 后续结果 | 关联 execution/task ID、状态、回执、可核验产物、用户评价；结果可晚到并形成新 revision |
| 提取元数据 | 输入快照版本、模型/提取器版本、处理状态、错误；不保存私有推理 |
| 修订与删除 | supersedes、撤销引用、删除代次；历史不能覆盖用户的新纠正 |

结果分别保存“未派发、已接收、运行中、Agent 自报成功/失败、宿主回执、用户评价”。Accepted 不等于完成；测试通过也不自动证明用户满意。没有可核验结果时保留 unknown，仍可学习明确选择，不能声称方法有效。

**EvidenceRef：证据由宿主绑定**

```text
EvidenceRef
  ref: ContextRef | HostActionRef | TaskReceiptRef
  origin: user | brain | agent | host
  scope + source_id + source_revision
  locator: message/turn ID + 可选原文位置
  completeness: full | truncated | unavailable
  content_hash + captured_at + retention_status
```

ContextRef 沿用现有协议。HostActionRef 和 TaskReceiptRef 是拟新增协议，分别指向已落盘的 UI 操作和真实执行回执。不能让模型构造来源 ID 后直接算作证据；宿主校验存在性、范围、内容与角色。模型的“用户偏好”陈述不属于用户原话。

原始正文保存在所属来源记录，纠正记录保存引用和必要快照。提议和替代方案全文须可恢复，不能依赖会变化的终端尾部缓存。引用过长时分页读取，不静默截断后宣称“完整”。沿用输入边界做大小校验；超限或缺页标为 incomplete，不参与习惯累计。

**一个完整例子，以下身份为示例数据**

| 项目 | 内容 |
| --- | --- |
| 原事项 | 项目 P / 画布 W / 区域 A / 根任务 T17 / 对话 C9：修复终端重连丢字 |
| 原建议 Q42 | “先重构整个 session 模块，再修复”；理由：“统一生命周期，减少后续复杂度” |
| 用户操作 U18 | 在 Q42 详情中输入：“改成先补复现测试，再做最小修复。今天要发版，重构另开任务。” |
| 明确原因 | “今天要发版”；原话定位到 U18，不推断用户永远反对重构 |
| 差异 | 范围由整个模块缩至当前故障；顺序增加复现；重构延后 |
| 候选偏好 | “临近发版修复已有故障时，倾向先复现，再局部修复，把重构另行安排” |
| 后续结果 | 新派发 T18 关联 T17 和 Q42；先记录 Accepted，验证回执到达后再更新 |
| 本事项下一步 | 建议先复现重连丢字，再修复并做定向回归；仍需用户点派发 |
| 新任务中的变化 | 满足 E 的生效条件后，同类发版修复优先建议最小修复；新功能架构设计不套用此偏好 |

## C 如何可靠关联，什么时候保持不确定

```flow
(收到用户反馈) -> {有精确提议引用?}
{有精确提议引用?} -> {身份范围版本有效?}: 有
{有精确提议引用?} -> {有可信同任务线索?}: 无
{身份范围版本有效?} -> *按原文区分意图: 是
{身份范围版本有效?} -> 拒绝绑定: 否
按原文区分意图 -> 明确替代
按原文区分意图 -> 暂缓或拒绝
明确替代 -> 可进入学习
暂缓或拒绝 -> 只记录本次决定
{有可信同任务线索?} -> 待关联观察: 有
{有可信同任务线索?} -> 独立输入: 无
待关联观察 --> 按原文区分意图: 用户选定原提议后复核
```

仅时间接近、Agent 同名、词义相似，都不能将观察升级为已关联。“待关联”不会增加偏好证据。

| 情况 | 归类与动作 | 是否形成习惯证据 |
| --- | --- | --- |
| 只点“忽略” | dismissed；未采纳原因未知 | 否；只处理这一条提议 |
| 指向 Q42 说“下周再做” | deferred；本事项暂缓 | 否；不推导反对该方法 |
| 指向 Q42 说“这个方案不采用” | rejected；保留原话 | 单独拒绝不足以归纳“更喜欢什么” |
| 从 Q42 的“改用其他方案”输入 B | replaced；宿主已携带精确 Q42 引用 | 是；完整原文保存后提取差异 |
| 点忽略后，直接问“帮我看登录页配色” | 无提议引用，可能换话题 | 否；原提议仍只记 dismissed |
| 同任务说“别重构，先补测试”，但无明确目标引用 | uncertain；可能针对 Agent 的其他建议 | P1 不自动配对；可由用户选定 Q42 |
| 同时存在两个相近提议 | unresolved；不选最近一条冒充目标 | 否；只有显式选择才能解除歧义 |
| 引用其他项目提议、失效会话或错误版本 | 拒绝绑定，保留独立输入 | 否；不跨范围寻找替代目标 |
| Agent 复述“用户喜欢最小修复” | agent-origin | 否；需回查真正用户输入 |

**P1 的可靠入口。** 提议详情增加“改用其他方案”；忽略后的历史详情保留同一入口。输入控件携带宿主创建的 proposal_ref，提交前再次核对版本与来源区域。输入和“派发替代任务”是两个动作；保存纠正不会发送任务。

带提议引用的 Dock 输入可以复用这条链。首期不靠自然语言中的“上一个”去找目标，也不自动抓取所有终端键盘输入。普通终端缺少完整用户回合或稳定任务身份时，只记录缺失，不制造精确性。

**任务身份缺失时。** 允许用户对选中的提议明确补充替代方案，这本身有可靠关联。宿主可生成 decision_episode_id，但它不是执行 task_id。没有独立根任务身份的经历，不能靠新建 UUID 冒充多个独立任务；仅用于本事项或由用户明确确认的偏好。

**入口身份约定。** root_task_episode_id 是“宿主任务根谱系”的稳定键，不由学习模型生成。它在第一次绑定时随 episode 落盘，重启复用。同根任务的重试、子任务和替代派发继承原键；同文案但真实独立的任务保持不同键。

| P1 入口 | 可信身份来源 | 能否累计独立任务证据 |
| --- | --- | --- |
| 提议关联真实派发回执 | AgentTaskReceipt.task_id、root_task_id、parent_task_id；宿主复核谱系，运行/对话引用另存 | 可以；缺失父链或关联来源时降级 |
| 带任务 ContextRef 的 Dock 纠正 | 宿主核实 task_id 对应真实任务，再核对 conversation_id 或原回合引用 | 可以；不能只相信模型传入的 ContextScope |
| 提议详情明确替代，但没有原任务身份 | proposal_id + HostActionRef；仅生成 decision_episode_id | 不能；本次纠正有效，可由用户明确确认习惯 |
| 只有 Thinking hook 标题或 Goal 文本 | 缺完整回合和根任务绑定 | 不能；不得按文本或时间补造身份 |

现有回执字段见 `crates/norma/src/protocol.rs:308`。P1 需要新增“提议与回执/原始回合绑定”的宿主适配；不是现有 Goal 事件已经提供了这些字段。会话切换或父链不完整时保留 partial，避免错算三次。

**时间的作用。** 时间仅用于排序和缩小待查看范围。长时间后仍有精确引用的纠正可以关联；几秒内到达但没有关联证据的输入，不能自动关联。

## D 模块边界、持久化与命令路径

**职责图：brain 做归纳，宿主掌握数据与权限。**

```flow
(用户操作) -> App宿主: 真实来源
App宿主 -> [(SQLite)]: 后台事务
App宿主 -> brain归纳: 转交已提交事件引用
brain归纳 -> norma命令: 读取证据与提交候选
norma命令 -> *App端点: token与范围核验
App端点 -> SQLite: 版本检查后保存
App端点 --> [(MemoryStore)]: P2用户确认后发布
group 推理域: brain归纳
group 宿主与持久化: App宿主, App端点, SQLite, MemoryStore
```

这些箭头表示消息和调用路径，不是新增 Cargo 依赖。brain 不接触数据库；读取和写入都通过 norma CLI 请求宿主。

**明确所有者，保持依赖方向**

| 模块 | 拟新增或调整的职责 | 不承担的职责 |
| --- | --- | --- |
| norma 协议 | 在 `crates/norma/src/protocol/learning.rs` 定义纯数据、校验与稳定引用；扩展 BrainOp/CLI | 不访问数据库、不调用 brain |
| brain | 在 `crates/brain/src/learning.rs` 组织归纳提示和有界任务；仍只依赖 norma 协议 | 不导入 agent/storage/runtime/GPUI，不直接写学习档案 |
| agent | 重导出 norma 的学习 DTO 给 storage；P2 接入已发布记忆 | 不依赖 brain，不新建另一套存储 |
| storage | 在 `crates/storage/src/learning_store.rs` 管理事务、幂等、候选与撤销；后台调用 | 不调用 brain 或 App；不决定用户授权 |
| app 宿主 | 在 `crates/app/src/app/brain_host/learning.rs` 绑定可信身份、控制任务和会话失效 | 不把模型分数当作事实或权限 |
| app 端点 | 在 `crates/app/src/norma/endpoint/brain_learning.rs` 执行鉴权后的受控请求 | 不让模型决定存储路径、项目归属或来源角色 |
| UI | 提议详情和 Norma 记忆设置增加学习视图 | 不绕过宿主直接写数据库 |

这些是预定文件，尚不存在。按职责拆分，Rust 单文件保持不超过 500 行。storage 通过已有 agent 依赖取得 norma 重导出的类型；不增加 storage → brain 或 brain → storage 边。

**P1 存储决策：SQLite 承载学习经历和候选，Markdown 保留长期记忆权威。**

| 数据 | 权威与事务边界 |
| --- | --- |
| 提议及其状态 | 提议队列从 JSON 一次性迁入 App SQLite；原文、状态和用户反馈可在同一事务提交 |
| 纠正事实与来源 | 新增 learning_events / episodes；关联已保存 ContextRef，或同事务写入完整 HostAction 来源 |
| 提取工作 | 同事务写入唯一 job；处理状态 pending / running / done / failed / cancelled；重启可恢复 |
| 候选偏好 | learning_candidates + evidence links；仅是可撤销的推断草稿，不同时写一份 Markdown |
| 使用记录与失效 | learning_uses、scope epoch、tombstone；记录实际注入的条目和版本 |
| P2 长期偏好 | MemoryStore 中的主题正文为唯一权威；SQLite 只保存来源、发布状态和引用，不再编辑同一候选正文 |

选择迁移提议队列，是为了避免“JSON 已移除，但纠正还没落盘”的两处提交窗口。只迁移提议，不迁移 GoalStore、审批日志或全部幕僚状态。导入键使用工作空间身份和原文件摘要；事务成功后标记已导入并停止旧文件写入。重启不重复导入，损坏文件保留并报错。旧提议缺少的来源仍标为未知，不追认历史偏好。

**一次操作的时序：保存成功后，才启动学习。**

```sequence num
participants: 用户, App宿主, SQLite, brain归纳, norma端点
用户 -> App宿主: 在原提议中提交替代方案
App宿主 --> 用户: 保存中
App宿主 -> SQLite: 一次事务保存反馈、提议状态和job
SQLite --> App宿主: 已提交的episode引用
App宿主 --> 用户: 纠正已保存
App宿主 -> brain归纳: 带范围的短期job token
brain归纳 -> norma端点: CLI读取本次完整证据
norma端点 --> brain归纳: 核验后的原文与引用
brain归纳 -> norma端点: CLI提交差异和候选
norma端点 -> SQLite: 去重、检查版本和删除代次
SQLite --> norma端点: 候选保存回执
norma端点 --> brain归纳: saved或conflict或suppressed
note 用户, norma端点: 以上流程没有派发任务
```

**保存与失败处理。** 点击反馈先显示“保存中”，后台提交成功才更新已保存状态、移除待处理项并安排归纳。失败保留可重试反馈；不要显示“已学会”。不阻塞 PTY、鼠标、输入路由或 GPUI 前台。关闭视图不会取消宿主已接收的持久化任务。

每次提交有宿主 action_id；相同 ID、相同内容返回原回执，相同 ID、不同内容报冲突。证据关系另有唯一键：candidate_id + root_task_episode_id + relation。重复 hook、CLI 重试、重启重放均不增加票数。迟到结果可更新 outcome，不产生第二次用户选择。

普通派发与学习写入不是一个外部事务。任务已接收而学习写入失败时，只修复来源记录，绝不重派任务。沿用 `crates/app/src/app/shared_context/action.rs:1` 的真实回执语义。

**拟新增 CLI 合约**

| 命令 | 输入与宿主验证 | 结果 |
| --- | --- | --- |
| `norma brain learning evidence` | episode 引用、版本；检查 token、范围、删除代次 | 有界完整证据，缺页提供续读标识 |
| `norma brain learning suggest` | job_id、expected_revision、差异与候选、已读证据引用 | saved / conflict / suppressed / invalid；宿主决定证据计数与状态 |
| `norma brain learning recall` | 当前事项 ContextRef；不能自填其他项目身份 | 可使用条目、适用条件、版本、scope epoch、证据摘要 |
| `norma brain propose` 扩展 | 原有参数 + 当前事项引用 + 学习快照标识 | 仍只创建待确认提议；宿主记录注入来源及模型声称使用的子集 |

所有模型动作经过 norma CLI。`crates/brain/src/acp/gate.rs:118` 目前只约束单条 brain 子命令，不能单靠它限制学习权限。新增归纳任务使用短期 job token，宿主只允许读该 job 的证据和提交候选。归纳进程不能 assign、decide、answer、修改权限或删除条目。

归纳会话还需独立 Gate：禁止直接 Read 项目文件，只放行对应 learning 命令。CLI token 不能限制适配器的直接文件工具，因此工具白名单和 Gate 必须一起收紧。当前主/审批会话共享的服务 token 要拆分为带 role 的凭据；删除只失效相关主会话和归纳 token，不轮换审批凭据。

**主会话也需要执行闸门。** 当前 `crates/app/src/app/brain_host/ops.rs:120` 会在 assign_followups=true 时允许直接 assign。P1 为接触过学习上下文的主会话设置宿主侧 propose-only 能力，直到重建会话。

即使自治开关已开，也拒绝该会话的 assign、decide 和直接 answer；不能通过省略学习引用绕过。审批 lane 使用独立权限，不注入学习上下文。用户从提议按钮确认派发仍走原有宿主执行链。

主会话每轮的学习快照由宿主绑定，包含 session/turn、注入条目版本和 scope epoch。不能只采信模型填写的使用清单。propose、report 及其持久化与交付队列都带该快照，在存储事务和最终展示/播报前复核。删除时清理相关待播报、Dock 回复与派生正文，不能只拦住最后的语音输出。

复用现有 ACP 客户端，按需创建隔离的短会话；不新增常驻第三个大脑。一次只处理一个已提交的纠正 job，有界超时和重试；失败仅标待重试。主会话与审批优先，归纳不占审批队列。没有明确纠正时不调用模型。

P2 的发布需要补充受控来源桥接。现有 MemorySourceReference 只有 UserTurn、ToolReceipt、SettingsEdit，不能冒用其中一种伪造自动学习来源。拟新增宿主验证的 LearningEvidence 引用，保留原始 lineage。Markdown 发布与 SQLite journal 用可恢复的发布回执衔接，不声称跨存储原子事务。

## E 候选偏好如何积累、使用与修正

**状态图：证据不足时观察，有冲突时停止套用。**

```flow
(一次明确替代) -> 待观察
待观察 -> *可作弱参考: 3个独立根任务且无冲突
待观察 -> 用户已确认: 用户明确以后适用
可作弱参考 -> 用户已确认: 用户确认情境与方法
可作弱参考 -> 有冲突: 出现同情境反例
用户已确认 -> 有冲突: 相反选择且原因不明
有冲突 -> 用户已确认: 用户纠正或明确例外
用户已确认 -> 已停用: 用户停用
已停用 -> 用户已确认: 用户重新启用
待观察 --> 已删除: 用户删除
可作弱参考 --> 已删除: 用户删除
有冲突 --> 已删除: 用户删除
用户已确认 --> 已删除: 用户删除
已停用 --> 已删除: 用户删除
```

图中的三次门槛是待评审推荐值；选择逐条确认模式时，达到门槛仍不能自动影响新任务。

**PreferenceCandidate 的最小模型**

| 字段 | 规则 |
| --- | --- |
| candidate_id、version、status | 状态为 observed / supported / confirmed / conflicted / disabled / deleted |
| scope | P1 限当前工作空间和来源区域内的项目工作树；不会自动扩到同仓库其他画布 |
| context_key、conditions、exceptions | 情境 + 决策维度 + 适用条件 + 例外；不只存一句宽泛偏好 |
| preferred_method、avoid_when | 倾向的方法及不适用场景；都属于可纠正的推断 |
| support、counterevidence | 保存独立 episode 引用集合；计数由宿主去重计算 |
| explicit_confirmation | 用户原话或设置编辑引用；没有就保持 inferred |
| lineage、supersedes | 原始来源、前版本、拆分或合并关系；可追到每次纠正 |
| last_observed、last_applied | 用于展示和后续评估，不单凭新旧决定真伪 |

**有限分类代替开放语义合并。** P1 将情境键限定为“发版前故障修复、一般故障修复、新功能、规划、未知”；维度限定为“处理范围、执行顺序、验证方式、优先级”。候选槽位为 scope + 情境键 + 维度，同槽位的相反方法作为冲突保留，不新建无关联条目。

方法值也使用对应维度的有限集合，例如局部修复/整体重构、先复现/先探索、定向验证/全量验证。模型只建议标签和原文依据；宿主检查枚举、来源与重复关系。未知情境、无法归入方法集合或附加条件无法核实时，保持 observed，不能自动达到三次门槛。

自由文本只用于解释与例外，不作为去重主键。P1 不尝试自动理解任意两段偏好是否语义等价。删除默认屏蔽整个候选槽位及其来源谱系，范围可能比一句话更宽，UI 须说明；同槽位要重新学习，需用户显式恢复。开放情境和精细语义归并放到 P3。

| 证据状态 | 对当前事项的影响 | 对新任务建议的影响 |
| --- | --- | --- |
| 一次明确替代 | 按用户本次选择调整建议 | observed；不泛化为稳定习惯 |
| 用户明确说“以后在发版修复中都这样做” | 作为明确指示 | confirmed；按限定情境生效 |
| 至少 3 个独立根任务支持，同情境无未解决反例 | 不覆盖当前明确要求 | supported；推荐仅作弱参考，阈值待用户评审 |
| 同情境出现相反选择，原因不明 | 遵循本次输入 | conflicted；暂停自动套用，保留双方证据 |
| 明确“这次例外，因为是线上事故” | 记录本次例外 | 原偏好不直接被推翻，增加有来源的适用边界 |
| 用户说“你理解错了，重写成……” | 保存纠正后的版本 | 新版本 supersedes 旧版本，旧版本停止召回 |
| 停用或删除 | 不再作为学习依据 | 从召回、队列和会话中撤销 |

3 是首版可验证的产品阈值建议，不是统计置信度。不要展示“87% 确定”这类无校准数字。同一个根任务的改写、子任务、重试和转交只算一次；纯采纳、沉默及系统自行提议不自动增加用户偏好证据，避免自我强化。

**使用顺序。** 当前明确要求优先；同事项纠正其次；用户明确确认的适用偏好再次。

达到证据门槛的推断仅供参考，条件不明时不应用。P1 只向主会话提供学习上下文，审批会话不接收这些偏好。

召回前先由宿主过滤范围、状态、epoch 和来源可用性，再按当前事项匹配情境。建议最多注入 3 条、总量不超过 8 KiB；超出按需读取，不能把所有历史塞进 prompt。初版不加向量库，不引入模型训练。

每条提议记录：注入的 candidate_id/version、模型声明使用的子集、当前事项、后续采纳或纠正。前者证明模型接触过什么；后者只是解释声明，不能证明模型内部因果。质量验收需同时观察实际建议内容。

**冲突例子。** 用户在另一次发版修复中要求“这次先整体重构”。若明确原因是旧架构导致无法局部修复，就补充例外；若没有原因，进入 conflicted，不能默默采用最新一句覆盖全部历史。P1 保留原情境槽位，由用户确认适用条件与例外；拆分为新的情境键留到 P3。

**范围推广。** P1 的狭窄范围是有意取舍。P2 使用宿主解析的 MemoryScope 归属，参考 `crates/storage/src/memory_access/binding.rs:72`。ContextScope 的 project_id 和 MemoryScope 的 project_id 不能假定相同。推广为项目共享或个人偏好时需显式选择；个人条目不携带项目代码、任务正文和私有路径。

## F 用户如何查看、纠正、停用和删除

**提议附近。** 详情并列显示原建议、用户替代方案和差异。状态用文字标明：仅本次、待观察、参考中、已确认、有冲突。建议旁提供“为什么这样建议”，可回看使用了哪些偏好与来源。

**集中管理。** 在设置 → Norma → 记忆中增加“学习记录”视图。复用现有列表、详情、搜索和范围选择的结构，不为候选草稿伪造 Markdown 主题。原始记录、候选偏好和已发布长期记忆用状态与类型区分。

| 用户动作 | 实际含义与反馈 |
| --- | --- |
| 查看依据 | 展示原提议、替代原话、明确原因、未知项、支持与反例；缺失来源如实显示 |
| “只是暂缓”或“不是针对这条提议” | 修正 episode 关系，移除它对候选的支持；重新计算状态 |
| 修改偏好或限定情境 | 保存用户明确版本及 edit_id；旧版本停止使用，显示保存结果 |
| “以后参考” | 将当前范围和情境下的候选确认为 confirmed；不触发派发 |
| 停用 | 保留记录供查看，停止召回；可再次启用 |
| 删除 | 删除候选正文及可追溯的学习派生副本，阻止旧来源重建；原任务对话另行保留 |

**删除必须是第一阶段能力。** 不能只从列表隐藏，也不能只删除一个 Markdown 文件。

```sequence num
participants: 用户, App宿主, SQLite, 旧会话与队列
用户 -> App宿主: 删除偏好
App宿主 -> App宿主: 先阻止相关学习输出交付
App宿主 -> SQLite: tombstone、epoch、正文清理与job取消
SQLite --> App宿主: 持久化完成
App宿主 -> 旧会话与队列: token失效、取消归纳、清理派生输出
旧会话与队列 --> App宿主: 旧轮次迟到结果
App宿主 -> App宿主: 版本已失效，拒绝写入和展示
App宿主 -> 旧会话与队列: 创建不含旧偏好的新会话
App宿主 --> 用户: 删除完成
note 用户, 旧会话与队列: 不撤回已确认执行的任务
```

1. 宿主收到删除后，立即在内存阻止受影响学习上下文继续交付。后台事务写入 tombstone、提升 scope epoch、删除候选正文及派生内容、取消相关 job。事务失败时保持“删除未完成”，本会话暂不使用，允许重试。
2. tombstone 仅保留必要的 ID、规范化偏好键、来源身份和截止版本。派生关系保留无正文的阻断标记。旧 episode 不得通过改名、合并或重新提取生成同一偏好。
3. 清理召回缓存，取消读过相关内容的归纳任务，重建受影响幕僚主会话。宿主使旧 token/epoch 失效，拒绝迟到的 suggest、report 和 propose。单靠 prompt 写“请忘记”无效。
4. 尚未派发的旧建议若用了该版本，标为依据已失效，需重新生成或用户显式重审。不得取消已获用户确认、已执行的任务；删除不撤回真实执行。
5. 删除回执只有在持久化和失效闸门均生效后才返回完成。重启加载 tombstone 后再恢复 job；旧快照导入和失败重试不能绕过当前权威库中的 tombstone。

整库恢复到删除前的系统备份会同时回滚 tombstone，P1 无法保证这一情况下的遗忘。产品内恢复必须保留当前删除账本；整库灾备恢复属于另一个恢复协议，不能宣称已经覆盖。

原始任务对话不是学习条目的副本，不因删偏好而整段删掉。学习提取入口必须排除已屏蔽的来源和派生记录；幕僚 context/history 的学习材料读取也要执行来源过滤。已有 history 文本转换会丢失身份，需在过滤前保留稳定 message/turn 引用，无法验证时不把片段作为学习材料。

删除的承诺是：系统不再召回、提取或使用被删除条目及其可追踪派生内容。不宣称擦除了已发送到外部模型的数据、系统备份或所有原始对话。用户后来直接提出相同要求，仍按当前要求处理；不能据此自动恢复已删除习惯。重新学习此情境需要用户显式恢复。

P2 发布长期记忆前，必须补齐 tombstone 检查。检查覆盖 MemoryAccess 读取、导入/恢复、合并和前台对话召回，并撤销相关语音/文字会话。现有 MemoryStore 的 Delete/restore 和关闭 recall 并不等于完整产品遗忘；这项补齐是 P2 的发布前置。

**交互设计落地。** 按 apple-design 的层级与用户控制原则，把常用操作放在原提议附近，详细证据按需展开。异步保存即时反馈，错误可重试。

使用 gpui-component，覆盖 hover、pressed、键盘 focus、selected、disabled。系统文案和状态支持中英文，用户原话不翻译。真实 App 验收覆盖浅色、深色、键盘操作及长文本，状态不只靠颜色表达。页面规范见 `.agents/skills/apple-design/SKILL.md`。

## G 分阶段实现与逐条验收

```timeline
P1a | 完整记录 | 可信关联、事务保存、去重和重启恢复
*P1b | 学到并用上 | 条件召回、冲突处理、用户管理和删除
P2 | 共享长期偏好 | 发布Markdown，接入前台与范围推广
P3 | 更多观察入口 | 终端、语音、手机的真实来源与消歧
```

**实施顺序；P1a 与 P1b 一起才构成推荐首阶段。**

| 阶段 | 交付 | 明确不包含 |
| --- | --- | --- |
| P1a 可靠经历 | 协议、提议存储迁移、精确引用入口、纠正记录、结果绑定、幂等与恢复 | 不启用候选影响建议；可作为内部里程碑 |
| P1b 学习与后续建议 | 受限归纳、候选累计、条件召回、使用记录、管理与删除、真实 App 证据 | 无自由文本自动配对，无跨范围推广 |
| P2 共享长期偏好 | 受控来源桥接、MemoryStore 发布、项目共享/个人范围、前台共用、完整撤销 | 不自动把项目细节推广到个人 |
| P3 扩展观察入口 | 有来源的终端/语音/手机回合；模型提出待关联建议，由用户消歧 | 不按时间或模型分数直接确立事实 |

实施前为每条行为先补失败测试。表中测试名为建议新增用例，**不是已通过记录**。B=brain 纯逻辑，S=storage，N=norma 协议，A=App 接入，E=真实 desktop-e2e。

| 编号 / 场景 | 构造与执行 | 必须同时成立的结果 | 层级 / 阶段 |
| --- | --- | --- | --- |
| T01 忽略后换话题 | 忽略 Q1；马上在同 Agent 输入登录页配色 | Q1 保存 dismissed；零替代关系、零偏好支持 | S+A+E / P1 |
| T02 同任务明确替代 | 从 Q1 详情提交 B，附明确原因 | 原方案和理由逐字保留；B、原因、来源准确；未自动派发 | N+S+A+E / P1 |

## H 尚需用户决定的取舍

下面四项是产品选择。星标为推荐值，不表示已经获得同意。技术底线已经固定：可靠来源、项目隔离、可纠正删除、执行权限不扩大。

```ask
首阶段覆盖哪些输入？
* 精确提议引用入口 | 做完整 P1；从详情和带引用 Dock 输入开始。
- 同时识别自由终端输入 | 增加真实回合身份采集和消歧 UI，扩大到 P3 的部分工作。
```

```ask
推断的偏好何时影响新任务？
* 三个独立任务后作弱参考 | 同情境无冲突才使用，标记为推断，可随时纠正。
- 用户逐条启用后才使用 | 自动整理证据，所有跨任务偏好需“以后参考”。
```

用户明确确认的偏好不必凑满三次。无论哪项，单次纠正都会立即影响原事项；都不会授权自动派发。

```ask
学习如何默认启用？
* 当前项目明确开启一次 | 开启后静默整理，不每次弹窗；管理页能关闭。
- 随幕僚默认开启 | 首次展示说明和关闭入口，需确认这一默认产品策略。
```

学习设置应区分“记录与整理”和“用于建议”。关闭前者取消未完成归纳并停止新增；关闭后者撤销已注入上下文。现有全局 memory.save=false / recall=false 分别作为更上层的禁止开关，不能被项目开关绕过。P1 设置改变不回收用户已有的任务输入。

```ask
未确认经历保留多久？
* 90 天无更新后清理 | 这是建议值；清理正文并让无有效依据的候选退出使用。
- 保留到用户手动删除 | 回顾更完整，磁盘和隐私成本更高。
```

已被用户确认的偏好以确认原话为独立来源，不因早期观察过期而自动丢失。删除 tombstone 的最小元数据不随普通保留期清理，否则旧任务重放可能恢复偏好。P2 推广为个人记忆仍需单独选择，不由上述开关自动开启。

**评审方式。** 优先确认首阶段入口和候选生效方式，再审查 B 的记录是否足够、C 是否会误关联、F 的删除是否符合预期。页面中的评审选择只生成反馈，不会修改 App 设置或执行任何任务。
