# Qwen3-ASR 0.6B 与语音指令、豆包、GPT-Live 的配合

状态：接入建议，未实施跨模式改造。2026-10-31 对照当前源码与 OpenAI 官方资料。沿用已有 A1 开发实现；本轮没有加载模型、打开麦克风或运行云端语音请求。

## 决策

Qwen 负责音频转写，Jev（若接入）负责快速意图与目标候选，现有 Norma Agent/工具执行卡片任务。豆包与 GPT-Live 是两种不同的对话入口：豆包当前可分离替换 ASR；GPT-Live 继续接收原始音频，Qwen 作为本地并行校对，改善后台任务依据。

首批优先完成已有 A1 单次语音指令的真实验收，然后接豆包单次指令，最后接 GPT-Live 的任务校对。连续监听需要额外的音频分段、队列和补充指令处理，不能只解除现有设置限制。

## 已有能力与缺口

| 入口 | 已有事实 | 需要补的工作 |
|---|---|---|
| 本地语音指令 | `LocalA1` 已注册；Zipformer CPU 预览、Qwen3-ASR 0.6B MLX8 / Metal 终稿；只提交有效终稿 | 固定运行时打包、真实麦克风与多轮验收；Jev 快速路由尚需单独实现 |
| 豆包 | 独立 ASR → `doubao-seed-2.0-mini` → 工具/TTS；当前 ASR 已开启二遍 | 让识别来源可选本地 A1，复用同一会话终稿入口和打断控制 |
| GPT-Live | 原生双工音频、client delegation、应用管理的后台任务；音频上传观察分支已存在 | Qwen 音频校对、来源/时间段/版本覆盖层、派发前就绪检查 |

已有 A1 是开发代码接入，不能等同于可发布。当前限制为 Apple Silicon macOS、单次 60 秒、一个活动录音槽。云模式和连续监听明确不允许启用 A1。实现和历史验证状态分别见 `docs/design-docs/2026-10-27-a1-local-asr-integration.md`、`docs/exec-plans/2026-10-27-a1-local-asr-implementation.md`。

## 1. 语音指令：让 Qwen 的终稿进入现有执行链

```text
一次麦克风采集 → 16 kHz 单声道 PCM16
                  ├─ Zipformer → 临时字幕
                  └─ Qwen 缓存原音频 → 松键后识别 → 终稿
                                                    ↓
                                   意图与目标候选（可接 Jev）
                                                    ↓
                                  当前卡片 ID / 范围 / 版本校验
                                                    ↓
                                      现有 Norma 工具执行一次
```

复用 `RecognizerFactory`、`RecognitionPipeline` 和 `handle_final_voice_text()`。现有桌面路径实际通过 ASR factory 解析 provider；不能因内部枚举叫 `AppleSpeech` 就声称已接 Apple 原生转写。

首版继续用已经验证过工件和参数的 MLX8 后端。Apple 预览或 Sherpa Qwen ONNX 可另做对照，但切换后端/量化必须重测；不能直接继承 MLX 的结果和速度。

Qwen 不直接发送任务，预览也不发送任务。Jev 只输出结构化候选，例如动作、候选卡片 ID、参数和未决项；目标不存在、重名或话术有否定冲突时，现有应用决定如何澄清。精确、简单请求可以走快速路由，复杂请求交给已有 Agent；同一条请求不能让 Jev 与 Agent 各自执行一次。当前检索的执行链未发现 Jev 集成，本段是新增设计。

## 2. 豆包：保留对话和声音，选择本地识别

```text
当前：麦克风 → 豆包 ASR（已含二遍）→ 豆包文本对话 → 工具 / 豆包 TTS
建议：麦克风 → A1（预览 + Qwen终稿）→ 同一豆包文本对话 → 同一工具 / TTS
```

这里的豆包是本项目当前的组合链路，不是泛指豆包所有端到端产品。`ChatRuntime::respond(transcript, turn, ...)` 已接收文本，因此无需改变豆包语言模型或音色，就能替换输入识别来源。

在 `plan.rs` 的输入选择处接 ASR 适配器，将本地终稿映射到当前 `SpeechEvent::HeldFinal(recording_id, text)`；先做按住说话。持续监听随后增加分段与输入结束策略，再映射到其会话入口。复用现有录音 ID、取消令牌和回执。

用户开口/按下录音时立即打断旧播放，不能等 Qwen 最终文字才打断。对话历史只加入最终选定的本次文字，云 ASR 和 Qwen 即使做 A/B 也只能有一个提交者。正常使用本地识别时不必继续上传同一音频到豆包 ASR。

本地 ASR 不等于整条链路离线：文字仍交给豆包，回复音频仍由豆包 TTS 生成。Qwen 不负责合成声音。

## 3. GPT-Live：保留原生听说，旁路校对后台任务

```text
同一条已采集音频
  ├─ 原上传链路 → GPT-Live 原生听说 / 插话 → client delegation
  └─ 有界音频复制 → 本地分段 → Qwen 候选转写
                                      ↓
                对齐本轮输入、选定任务文字、检查是否可以执行
                                      ↓
                     现有后台 NormaSession / 卡片工具
                                      ↓
                       真实回执 → GPT-Live 讲给用户
```

GPT-Live 自己听原音频。官方提供的是应用侧 client delegation 和上下文追加接口，没有本次核验可依据的“将内部识别器切成 Qwen”接口。只修改字幕不会自动修正 Live 对音频的理解；把音频先转文字再当上下文追加，也不能宣称等价保留原生双工。[O1][O2]

可在现有 `observe_uploaded_audio()` 的观察分支有界复制 PCM。复制/入队不能等待 Qwen 推理或阻塞 Live 音频上传；不再打开第二个麦克风，继续使用原双工音频处理。Qwen 结果需要独立记录 `source`、本地音频段、`revision`、会话代次、完成/失败状态。

`session.delegation.created` 只有委派信息，不携带完整用户话术。转写片段也不表示用户说完。不能把 `offset_ms` 当作句末，或将本地上传样本数直接当成服务转写时轴。[O1] 本地 VAD、按住释放、语义完成判断用于候选边界；末尾出现“但是 / 不要”或音频覆盖不足时，不能按半句执行。

任务请求先关联到明确的本地语音段及当前转写版本。匹配可靠且 Qwen 终稿就绪时，用选定文字构造 `NormaSession` 请求。若校对未完成，任务可以等待，Live 听说继续；若匹配不可靠或关键名称冲突，说明疑点并让用户短确认。禁止无声地用旧草稿冒充校对终稿。

同一任务仍由现有后台唯一执行。新转写在执行前改变了意图时，使旧规划失效；已有副作用后再出现更正，应作为更改/取消请求处理，不能重跑或声称已自动撤销。按当前持久回执记录去重，不能只靠某次请求的内存布尔值。

选定的识别修订与真实任务事实可以用 `session.thinking.append` 补充给 Live；需要说出的结果用 `session.commentary.append`。相关更新关联原 `delegation_id`。内容作为来源明确的资料，不把原始识别文本当作开发者指令。追加确认只说明服务收到资料，不证明已更正所有理解、说出口或用户已听到。[O1]

此方案直接改善后台派发依据，不能保证所有即时口头回复都先经过 Qwen。若产品要求口头回复也只依赖 Qwen 终稿，就需要另设“ASR → 文本模型 → TTS”模式，并接受其与原生双工的体验差别。

## 引擎与音频资源怎样共享

- 复用 A1 受管 worker 和固定模型工件。单次输入仍使用现有双模型组合；Live 需要把 Qwen 终稿角色从预览组合中解耦，避免为旁路校对额外运行无用的 Zipformer。
- 全 App 共享模型宿主，限制一个 Qwen 推理槽；模式切换先取消旧会话，再转移使用权，不为每张卡片各加载模型。
- 持续音频先进入有界分段缓存，推理在后台。现有单录音 A1 接口不能无修改承接整场通话。过载必须显式标记校对未完成；只丢弃被同轮新版本取代的工作，不能静默丢掉另一条真实指令。
- 保留现有单段 60 秒上限，连续通话需独立定义分段与多段指令拼接。缓存覆盖不足时要求补充，不能凭残音执行。
- 模型下载/安装与推理分离；固定权重、tokenizer、解释器和原生依赖，进行完整性校验。当前开发入口依赖本机目录，发布包必须自带受管运行时。
- 加载、结束识别、IPC、资源回收均在后台。首次加载与暖运行分开计时；保留现有内存压力保护。按实验记录评估双模型约 2 GiB 级别进程占用，但实际 App 资源和时延仍待验收，不能仅凭 0.6B 宣称轻量。

## 代码落点与分阶段验收

| 顺序 | 范围 | 交付与验收 |
|---|---|---|
| 1 | `crates/asr/src/providers/local/a1/host.rs`、`crates/asr/runtime/a1/worker.py` | 复用已有适配，完成单次麦克风、模型复用、超时、取消和真实运行时验收 |
| 2 | `crates/app/src/app/doubao/plan.rs`、`crates/app/src/app/doubao/plan/conversation.rs` | 本地识别接同一终稿入口；只更新一次历史、一次执行，开口可立即打断旧播放 |
| 3 | `crates/app/src/app/gpt_live/session.rs`、`crates/app/src/app/gpt_live/bridge.rs`、`crates/app/src/app/gpt_live/dispatch.rs` | 音频分流、校对覆盖层和后台请求接缝；先旁路记录，再验证派发就绪检查 |
| 4 | ASR 设置、模式兼容与运行时打包 | 识别与对话来源分别配置；模式切换不残留模型/收音；签名后在独立安装环境验证 |

阶段 3 的旁路记录只用于开发评估：记录最小时间/版本/结果指标，转写和音频不默认持久化。观察阶段不得改变实际派发；启用派发校对后，同一模式必须有明确就绪和降级状态。

建议以同一小组录音覆盖：英文卡片名、句内混合、否定词、停顿后补充、快速连说两条、取消后迟到终稿、模式切换、模型异常。测首次字幕、停口到终稿、任务开始和真实声音反馈，不能把单模型 decode 时间当端到端体验。

| 验收要求 | 计划证据（本轮未执行） |
|---|---|
| Partial 不提交、Final 不重复、空/失败不冒用预览 | ASR 与单次输入聚焦单元/集成测试 |
| 豆包切识别来源后对话/TTS正常、立即打断 | 豆包会话测试与真实麦克风/App 场景 |
| Live 上传不被本地推理堵塞，关联与修订有效 | bounded 队列、时轴、revision、取消、委派去重的假上游测试 |
| 后半句改变指令，已执行后不会重复执行 | 后台规划与持久回执集成测试、真实对话验收 |
| 配置状态清晰、可取消、中英文一致 | 定向 desktop-e2e；i18n 检查 |
| 发布后独立运行、回收干净 | 签名安装包与冷启动/退出/多轮真实验收 |

界面设计沿用已加载的 Apple 设计技能：字幕及时响应、原位修订；“正在识别 / 校对中 / 已提交”明确区分；取消始终可用。菜单沿用现有紧凑选择器，不能把“识别来源”混成“对话模型”。本轮只提出状态与验收要求，没有修改产品界面。
