# 桌面 Voice 接入豆包全双工 SPEC

状态：`本地实现与假上游 E2E 已完成；真实服务鉴权待验证` · 2026-09-29

## Problem Statement

Norma OS 桌面 Voice 目前只有单次语音指令与持续聆听：麦克风音频经 ASR 得到最终转写，再交给 Norma Master Agent，最后由 TTS 播报。用户希望保留这套已能使用的语音指令，同时获得可以边听边说、自然插话的豆包全双工通话。直接把豆包当作另一个 ASR 或 TTS Provider，无法提供全双工对话；另做一套项目工具又会导致权限、任务和回执语义分叉。

用户还要求豆包模式沿用现有 Norma 人设和当前项目信息，能够通过现有项目工具操作 AgentCard、任务、Terminal 与 Canvas，并在 Settings 中明确切换模式。旧语音链路、配置和聊天记录不应因新增模式而改变。

## Solution

Settings → Voice Setup 顶部提供“现有模式／豆包双工”选择。现有模式继续使用单次语音指令或持续聆听以及原有 ASR → Norma Master Agent → TTS 链路；豆包模式建立独立的 Seeduplex 3.0 实时会话，由豆包处理持续音频输入、对话和语音输出。`⌘E` 启动或结束当前选定的模式，切换模式时结束旧语音会话；两侧配置各自保留。

豆包会话从现有 Norma 提示词组装入口获得人设、当前项目、Agent 名册及当前画布上下文。普通口语回复由豆包直接说出，不再向桌面 Norma 模型提交同一段语音。豆包提出项目工具调用时，桌面先根据用户实际转写、当前项目和稳定调用 ID 校验，再复用现有工具定义、工具运行时和桌面 AgentCardAdapter；真实回执以原调用 ID 返回豆包。工具已接收不等于任务已完成。豆包对话独立于旧项目聊天历史，首版不自动写回历史，也不保存原始音频。

## User Stories

1. 作为桌面用户，我想在 Voice Setup 顶部选择现有模式或豆包双工，以便按需要使用语音指令或自然通话。
2. 作为现有语音用户，我想继续使用单次语音指令，以便原来的 Hold／Toggle 操作保持熟悉。
3. 作为现有语音用户，我想继续使用持续聆听，以便原来的 VAD 分段、Agent 回合和 TTS 回复保持可用。
4. 作为桌面用户，我想 `⌘E` 始终操作当前选定的语音模式，以便不必记忆第二个快捷键。
5. 作为切换模式的用户，我想旧通话立即结束且两种模式各自保留配置，以便不会听到旧模式迟到的回复。
6. 作为首次配置豆包的用户，我想在 Voice Setup 输入并保存具备 Seeduplex 3.0 权限的豆包语音 API Key，以便建立双工会话。
7. 作为重返设置页的用户，我想看到凭据已保存但看不到密钥明文，以便确认配置而不泄露凭据。
8. 作为凭据失效的用户，我想得到明确的修复提示，以便不会被错误引导去安装旧模式的 ASR 或 TTS。
9. 作为豆包用户，我想通过 Mac 内置扬声器和麦克风免提通话，以便不必强制佩戴耳机。
10. 作为使用耳机的豆包用户，我想使用系统选定的输入和输出设备，以便保持既有音频设备习惯。
11. 作为豆包用户，我想在 Norma 说话时插话并立刻停止旧音频，以便自然改变话题。
12. 作为豆包用户，我想插话后继续保持通话和收音，以便不用重新启动会话。
13. 作为豆包用户，我想听到与现有 Norma 一致的人设和说话方式，以便切换模式后仍在和同一位助手交流。
14. 作为已打开项目的用户，我想豆包知道当前项目和可用 Agent，以便可以说“这个项目”和 Agent 的呼叫名。
15. 作为切换项目的用户，我想旧豆包会话结束，以便旧项目上下文不能用于新项目操作。
16. 作为尚未打开项目的用户，我想普通语音对话仍有明确状态，而项目操作被拒绝，以便不会猜测操作位置。
17. 作为只想讨论的用户，我想豆包回答问题而不触发写操作，以便想法讨论不会变成派工。
18. 作为明确要求执行的用户，我想豆包调用现有 Norma 工具，以便项目操作与文字和原语音模式一致。
19. 作为要求向现有 Agent 派工的用户，我想任务进入原 AgentCard 队列并返回真实 task_id，以便可以追踪执行。
20. 作为要求查看任务的用户，我想豆包通过现有只读工具获取实时状态，以便不会把旧提示词快照当成当前进度。
21. 作为确认了上一轮唯一明确操作的用户，我想“可以”“继续”能结合上一轮上下文生效，以便无需重述完整任务。
22. 作为表达含糊确认的用户，我想 Norma 先澄清目标，以便不能把模型猜测当作我的执行授权。
23. 作为要求关闭或删除卡片的用户，我想现有精确目标校验继续生效，以便不会误删别的卡片。
24. 作为派出长任务的用户，我想先听到“已接收／已排队”的真实回执并继续对话，以便不用等待 Agent 完成才能说下一句。
25. 作为等待结果的用户，我想仅在收到真实终态证据后听到完成或失败报告，以便不会把接收任务误认为完成任务。
26. 作为在任务执行中插话的用户，我想只打断豆包播报而不取消已接收的项目任务，以便口头插话不会破坏正在进行的工作。
27. 作为明确说“取消任务”的用户，我想取消指向原 task_id，以便取消行为可验证且不会影响其他任务。
28. 作为遇到网络断线的用户，我想看到通话已断开且不会自动切入旧模式，以便知道自己正在使用哪条语音链路。
29. 作为网络重连的用户，我想同一工具调用不会重复派工，以便断线重放不会重复修改项目。
30. 作为执行回执未知的用户，我想得到“结果待核对”而不是自动重试或宣称成功，以便避免重复副作用。
31. 作为有隐私顾虑的用户，我想原始音频和豆包通话不自动保存到旧聊天记录，以便新模式不会改变旧会话内容。
32. 作为维护者，我想豆包只增加连接与事件适配并复用现有工具执行边界，以便后续修复权限或任务行为时只有一个事实来源。
33. 作为 QA，我想使用假豆包上游完成设置、语音、工具、打断和断线验收，以便日常回归不消耗真实账号额度。
34. 作为 QA，我想用真实 App、真实麦克风与内置扬声器做专项验收，以便确认回声消除、插话和播报在硬件上可用。

## Implementation Decisions

- 在 Voice 入口增加一层持久化的顶级模式选择。原有 `SingleVoiceCommand`／`ContinuousListening` 仍只控制链式模式内部行为；不把全双工硬塞入两者共享的回合状态机。默认选择现有模式，升级后旧配置语义不变。
- Voice Setup 顶部展示模式选择、各自就绪状态和当前模式的修复操作。链式模式继续要求麦克风、ASR、Agent Provider、TTS；豆包的配置就绪只要求麦克风、音频输出与豆包凭据，启动后的连接中／已连接／断开另行展示，不以尚未发起连接作为设置未就绪的理由。豆包普通聊天不要求旧 ASR／TTS 配置或调用桌面第二个模型。
- 两种模式共用 `⌘E` 和现有麦克风权限、PCM 处理与播放基础。豆包首版使用 macOS 系统默认输入与输出设备，设置页明确显示这一点；应用内输入设备选择器只留在现有模式。模式或项目切换时停止当前会话并丢弃迟到事件；不自动重新打开麦克风。已由 AgentCard 接收的任务按任务自身生命周期继续运行。
- 豆包连接层独立处理其 WebSocket 鉴权、音频格式、事件、会话关闭与重连。输入以协议要求的 16 kHz 单声道 PCM16 流发送；输出若为压缩音频，必须在后台解码为现有播放器接受的 PCM。音频与网络处理不能阻塞 GPUI 前台。
- 对话路径以低延迟为目标：麦克风每 20 毫秒发送一帧 PCM；双工输入队列最多保留约 160 毫秒音频，饱和时丢弃最旧帧；收到回复音频后立即排队播放。普通回复不再经过桌面第二次 LLM 或独立 TTS。真实首音延迟及 p50／p95 只能在具备服务权限后用真实麦克风和输出设备测量。
- 豆包双工会话可同时处于收音和播音状态，不能复用只允许 Listening／Thinking／Speaking 互斥的旧 DialoguePhase。用户插话时立即停止播放并清空待播旧音频；内置扬声器免提必须经过真实设备的回声消除验收，不能仅凭耳机测试通过。
- 会话建立时调用现有 Norma 提示词组装逻辑，完整保留人设、工具规则、当前项目、Agent 名册和当前画布上下文；仅做豆包协议字段适配，不维护另一份静态人设。项目变更后建立新会话并重取上下文。动态项目数据不是授权指令，执行前仍要查实时状态。
- 将现有 Norma 工具定义映射为豆包 Function Calling 声明。收到完成的函数调用事件后，用用户实际转写、会话绑定项目、工具名和参数建立 ToolContext；普通对话不提交第二个 `UserTurn`，也不触发第二个 Norma 模型回合。
- 项目操作复用现有 NormaToolRuntime 的参数解析、删除目标校验和桌面 AgentCardAdapter 的真实副作用。豆包事件适配器只负责协议转换、授权与回执关联，不实现第二套 Canvas／Terminal／AgentCard 操作。
- 写工具必须在应用侧验证用户真实执行意图；当前保守语音授权规则可复用，但“可以”“继续”只在上一轮存在唯一待确认动作且项目与目标未变化时才能授权。缺少最终转写、授权含糊或目标变化时拒绝写操作并要求澄清，不相信模型声称的授权。
- 工具按模型调用顺序串行执行。以会话、项目及 `call_id` 形成稳定操作身份；重复事件、断线重放和迟到结果不能再次执行副作用。需要桌面可恢复的操作回执状态；若崩溃发生在提交之后而结果不可证实，标记 `unknown`，禁止自动重派。
- 每个工具结果用相同 `call_id` 回传豆包。`accepted`／`queued` 只可播报已接收或已排队；任务完成、失败或取消只能依据现有 AgentCard 真实终态播报。长任务接收后豆包可继续对话；语音插话不等于取消任务，明确取消才走现有取消工具。
- 豆包 API Key 通过现有 macOS Keychain 凭据边界保存；持久设置只保存非敏感配置及 Keychain 引用。网络请求、常规日志、诊断、截图和测试 fixture 不包含密钥或完整用户语音内容。
- 豆包通话上下文仅在该会话内维持。首版不将转写、回复或音频自动写入旧项目聊天历史；切换模式、项目或重启 App 后不暗中续接旧通话。
- 界面遵循现有 Voice Setup 和 macOS 设计语言：模式选择清晰可见，连接中、就绪、断开、凭据错误、麦克风不可用都有明确状态；可点击控件提供 hover、pressed、focus、selected 与 disabled 反馈。

## Testing Decisions

- 主验收接缝是现有桌面 Voice 的应用级 e2e：通过 Settings 选择模式和 `⌘E` 进入真实 App 状态机，使用本地假豆包 WebSocket 上游驱动音频与函数事件，并在真实桌面工具 Adapter 边界观察用户可见回执及项目副作用。优先扩展该接缝，不为每个模块另建测试入口。
- 好测试断言外部行为：选中了哪种模式、哪段音频被播报或停止、哪个任务确实进入 AgentCard 队列、哪个工具未执行、回执是否与同一调用对应。不要只断言内部枚举、消息两边 ID 自洽或 mock 被调用。
- 模式与设置 e2e 覆盖：升级默认仍进旧链路；旧 Single／Continuous、Hold／Toggle 与 `⌘E` 不变；豆包设置保存和重载；两侧配置独立；切换时旧通话停止且迟到音频无效；豆包就绪不被旧 ASR／TTS 配置阻断。
- 提示词 e2e 覆盖：假上游收到现有人设及当前项目/Agent/画布信息；项目切换后新会话只含新项目上下文；普通聊天不创建第二个 Norma 模型回合或项目任务。
- 工具 e2e 覆盖：豆包函数调用经已有工具定义和桌面 Adapter 产生具体 task_id 或卡片操作；真实转写缺失、讨论语气、错误目标和未授权删除均不得执行；唯一上下文中的“可以”可执行，含糊“可以”不可执行。
- 去重 e2e 覆盖：重复 `call_id`、断线重放、项目切换后的迟到调用和提交后回执未知；明确断言每个写操作至多发生一次，`unknown` 不自动重派。多工具调用保持顺序，失败不抹掉已成功的真实回执。
- 音频与生命周期 e2e 覆盖：说话时播放、播报中插话、播放器队列清空、长任务回执后继续对话、明确取消任务、网络/凭据/权限错误、断线不静默切到旧模式；不保存原始音频或把豆包对话写入旧聊天历史。
- 协议解析、音频格式转换和稳定操作身份只补必要的聚焦测试；沿用现有 Voice Settings、Voice 模式和移动实时工具回执测试的先例。所有新增单测遵守仓库规定的完整场景注释、数值推导及带说明的具体正反断言。
- 真实 L3 验收在隔离项目中使用本机 Keychain 凭据，核对豆包全双工权限和 Function Calling 握手，并分别用耳机、Mac 内置扬声器与真实麦克风验证回声、插话及播报。该结果与假上游测试分开报告；账号未获授权时不得把假上游通过报告成真实全双工可用。
- Settings 与语音状态的视觉变更必须用 Computer Use 操作真实 `.app` 验收；headless GPUI e2e、静态图及截图只能补充。改动按仓库范围运行 app 检查、e2e、受影响 crate 测试和机械化护栏。

## Out of Scope

- GPT-Live 的实现、设置项或为未来 Provider 增加只有豆包一个实现的抽象层。
- 将截图中的 ASR 2.0 或 TTS 2.0 单独注册为现有 ASR／TTS Provider；它们不是本次全双工的前置条件。
- 修改现有单次语音指令、持续聆听、Norma Master Agent 或 TTS 的业务语义。
- 改造 iOS 云语音网关、手机配对或跨设备任务授权。
- 把豆包语音转写、回复、工具结果自动合并到旧聊天历史或工作线程；保存原始通话音频。
- 以模型文本、旧项目快照或仅收到 `accepted` 作为项目任务完成证据。

## Further Notes

- 本规格依据已确认的模式切换图、技术架构图、工具复用图及豆包 API 调研。图示用于理解连接点；真实接口以实现时的官方协议和账号握手为准。
- ADR-0013 保持对两种现有语音交互模式的共享回合运行时约束；豆包是新的顶层实时会话，不能把其同时听说强行编码进旧互斥状态。Master Agent 的“一个工具执行事实来源”仍成立：一次语音输入仅由当前选定的模型发起工具调用，真实副作用始终经过同一桌面 Adapter。
- 本地测试凭据须存 macOS Keychain；已提供的截图只展示 ASR 2.0／TTS 2.0 配置，尚不能证明 Seeduplex 3.0 授权。Issue 与仓库均不得包含密钥值；真实联调需单独确认目标资源、账号配额和 Function Calling 能力。
- 研究阶段已发现现有工具运行时只缓存已完成的内存回执，且保守语音授权规则不能单独理解“可以／继续”。这两项是桌面全双工接入必须补齐的行为，不要求改变旧模式的执行路径。
