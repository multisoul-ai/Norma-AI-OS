# Agent 执行效率与提交完整性

本规范让 Agent 按变更风险选择最小充分流程：快不等于跳过验证，而是不做与当前范围无关的工作。

## 执行分级

| 变更范围 | 实施流程 | 提交前验证 |
|---|---|---|
| 单 crate、纯逻辑、目标明确 | 定位 seam → 先写一条失败测试 → 最小实现；不自动启动审查子任务 | 开发中运行聚焦测试；提交前运行受影响 crate 的测试 |
| 跨 crate 或有明确用户流程 | 在上述基础上补集成测试与真实 App 证据 | 受影响 crate 测试，加真实 App 或跨 crate 验证 |
| 发布、持久化、并发、权限或安全边界 | 先明确验收与风险；可按需正式审查 | 完整验收矩阵及发布检查 |

只有用户明确要求 code review/正式 spec，或改动属于第三行时，才使用会强制全量测试和并行审查的重型 skill。对第一行任务，不得因为历史调查、可选 skill 或无关工作区失败扩大验证范围。

若 15 分钟内尚未得到聚焦测试的绿灯，Agent 必须报告具体阻塞和已运行命令；不得继续无边界地调查。

## 合并与增量验证

先按用户当前要求区分功能开发、局部修复和仅提交/合并，再确定验证范围。合并分支包含 UI 或跨 crate 代码，本身不代表需要重新执行开发验收。

- **仅提交/合并**：检查分支与工作区，保留双方意图并解决冲突，运行正常提交钩子和冲突所需的编译/聚焦检查，确认目标分支包含预期提交后收尾。默认不额外启动正式 review、全仓测试、release 构建或完整桌面验收。
- **复用证据**：同一实现已有通过记录，且相关代码、依赖、配置与运行条件未改变时，引用验证基准、命令结果和证据路径；仅补充因本次差异而失效的检查。提交钩子仍照常执行。
- **处理发现**：合并引入的回归按最小修复处理并定向验证；无关的既有问题记录后继续收尾，不自动扩展为功能改进。数据丢失、安全或核心流程不可用等阻塞问题必须处理或明确报告。
- **局部 UI 修复**：选覆盖该差异的最小现有场景，只查看对应的关键截图。最小场景顺带执行的其他步骤、产出的其他截图，不自动扩大人工验收范围；也不为减少读图而另建整套场景。
- **扩大验证**：用户明确要求完整验收，或具体差异、失败证据表明影响更广时，才扩大相应检查，并先简述原因。已通过的检查，仅在新改动、失败或证据失效时重跑。

详细验收记录可保留在证据文件中；面向用户优先报告结果、必要限制和记录入口，不逐张展示无关截图。完整 UI 验收仍覆盖其范围内的全部关键视觉项，不能把局部通过声明为整套通过。

## 对抗式代码 Review

- 凡进行代码 review，必须调用至少一个独立 subagent 做对抗式审查，不能只由实现者自审；用户已授权此后代码 review 使用 subagent，无需重复询问。
- 给 reviewer 明确的基准、改动范围、需求与规范，要求独立寻找能推翻实现正确性的具体反例，重点检查边界、取消与并发、遗漏要求、测试假阳性；不预设“应当通过”或强制凑问题数量。
- 审查默认只读。主 Agent 核验发现、去重并按严重性报告，附文件位置、触发条件、影响与证据，区分既有问题和新引入问题，以及已复现事实和未验证推测。
- 此规则约束代码 review 的执行方式，不要求每次普通开发或合并自动发起正式 review，也不自动扩大测试或全仓审查范围；合并审查聚焦冲突处理与集成差异。

## Git 提交完整性

Agent **不得**使用 `git commit --no-verify`、`git commit -n`，也不得通过修改、取消或替换 `core.hooksPath` 来绕过 hook。验证失败时只能修复、缩小到正确的验证范围，或向用户报告阻塞；不能跳过验证提交。

Git 的 `--no-verify` 会在客户端直接跳过 hook，无法由 pre-commit 自身拦截。因此仓库规则只能约束 Agent 行为；要技术性阻止未验证代码进入共享分支，还必须在代码托管平台上为 `dev`/`main`：

1. 限制直接推送，只允许通过 pull request 合并。
2. 将 CI 的 `rust checks` 设为必需状态检查。
3. 禁止管理员绕过上述规则（若平台支持）。

CI 应覆盖 `dev` 与 `main` 的推送，作为本地 hook 被跳过时的服务端兜底。
